# Architecture — Disney World Park Pulse

Last updated: 2026-10-18. Describes the locally accepted multi-file candidate; see PROJECT_STATUS.md for deployment status.

## System overview
The browser receives static HTML, CSS, JavaScript and images from GitHub Pages (or a local development server). JavaScript requests public read APIs from two Cloudflare Workers. The Workers collect external data and share a D1 database. The frontend does not connect directly to D1.

    Static host / local HTTP server
           |
           v
    Browser: index.html + assets + images
           |                         |
           v                         v
    Queue/history Worker       Weather Worker
           |                         |
           +----- shared D1 DB ------+

The repository also has a separate Python static-data collector. It is not a drop-in replacement for the Worker APIs.

## APIs and response contracts
Queue origin: https://wdw-queue-probe.jacocksr.workers.dev
Weather endpoint: https://park-pulse-weather.jacocksr.workers.dev/api/weather

| Route | Main contract | Worker cache TTL |
|---|---|---|
| /api/live-wait-times | updated_at; parks[key] with metadata, crowd_score, hours and rides | 60 seconds |
| /api/history-24h | updated_at; rides[id].points as [ISO timestamp, wait]; optional hours metadata | 120 seconds |
| /api/historical-summary | rides[id].buckets[weekday_hour] averages/samples; recent summaries; daily_heatmap | 900 seconds |
| /api/ride-history?ride=ID | ride; days[YYYY-MM-DD] with [epoch seconds, wait] points; up to 14 archived days | 600 seconds |
| /api/closure-events | schema_version 1; tracking/coverage metadata; event IDs, sampled transitions, category/state/uncertainty | 120 seconds |
| Weather /api/weather | schema_version 1; parks with observations, forecasts, alerts, collection success/errors and freshness | 60 seconds |

Cache timestamps and successful HTTP responses do not guarantee fresh source observations. Preserve source timestamps and stale/unavailable states.

## Data semantics to preserve
- Eastern park-calendar dates and weekday/hour buckets; display-time selection is distinct.
- Live snapshot, rolling history and archived day points have different timestamp representations.
- Effective card averages use positive finite numeric waits from qualifying open standard attractions.
- Matched comparisons average matched attractions equally, track eligible/matched counts and gate on summed historical samples. They are not sample-weighted park averages.
- Backend crowd score uses positive waits and an absolute mean-wait formula (mean / 7, rounded and clamped 1–10). It is distinct from matched percent-versus-typical; existing UI wording discrepancies are tracked separately.
- Zero wait, missing observation and reported closure are different states. Different views intentionally have different inclusion rules.
- Closure times are sampled bounds, not exact transitions or causes. Keep unknown starts, interruptions, refurbishments and scheduled experiences distinct.
- Maintained event descriptions/dates do not establish live ticket inventory or showtimes.

## Workers and D1
Queue source reference v3.7: all-four-park collection; 08:30 to before 24:00 Eastern collection window; hours prefetch; hourly/day rollups; bounded archive processing; forward closure tracking.
Weather source reference v1.1: NWS discovery, primary-station sharing, observation collection, forecasts, alerts, collection state and usage logging.
Both owner-reported schedules: every five minutes. Shared binding: env.DB -> wdw-busyness-db.

Queue tables: queue_times, ride_hour_summary, ride_day_summary, rollup_state, ride_day_points, closure_tracking_state, ride_closure_events.
Weather tables: weather_locations, weather_collection_state, weather_observations, weather_alerts, weather_alert_locations.
Shared table: api_cache; application cache keys are separate. Do not alter _cf_KV as part of application refactoring.

Supplied schema includes revision CHECK(revision >= 0), which queue tracking's guard relies on. Presence of initialized state rows and runtime concurrency behavior are not established by schema review alone. Weather positional inserts currently match supplied table column order. Review schema changes against both Workers.

Secrets must never go in frontend, fixtures or committed configuration. Public API addresses are not database credentials. Worker source/configuration and D1 migrations should eventually be versioned as a separate reviewed backend task; they are not silently recreated from chat memory.

## Development and tests
Normal candidate: no build step; optional local server from repository root:

    python3 -m http.server 8000 --bind 127.0.0.1

Open http://127.0.0.1:8000/ . The server serves static files; the browser still uses deployed APIs. Stop with Control+C.

Extraction verification:

    python3 tests/verify_source.py

This is an initial-baseline hash check, not a permanent regression gate after intentional edits. Do not update hashes merely to hide unintended changes.

Optional browser replay (requires Python, Playwright, Chromium and the owner's HAR):

    python3 -m pip install playwright
    python3 -m playwright install chromium
    python3 tests/check_candidate.py /path/to/networktest.har

The delivered harness freezes time, replays captured resources, compares original/candidate settled states and blocks missing requests. Keep raw HAR local; do not publish it without review. tests/reference.html is immutable original test input, not another editable application. Full archived response fixtures, alert scenarios and motion/accessibility coverage remain limitations.
